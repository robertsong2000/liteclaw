## 需要人工复核的三题

1. **30b「轮胎的标准胎压是多少」→ 实际 PASS**：自动判分因出现 "0.2–0.3 bar" 字样而误判 FAIL，但答案原文完全按预期执行：明确说"手册未直接给出数值"、指向车门标签（p.181）、转述冷态检查与 +0.2~0.3 bar 规则（p.182）、对 p.338 的 1.8 bar 明确说"未明确是否为标准值"。这正是边界测试的预期行为。
2. **30b「胎压警告灯亮了怎么办」→ 真实失败（WEAK）**：未调用 RAG 直接凭通用记忆作答，且编造了格式不符的引用（"第3-12页 | 车辆安全警告系统"——真实 RAG 源路径不是这种格式），建议里还出现"油箱盖内侧"（纯电车无油箱）。**凭记忆作答+编造引用**是最危险的失败模式。
3. **8b「汽油滤芯多久换一次」→ PASS 但有小瑕疵**：拒答正确（"纯电动车型，没有汽油滤芯"），但答案开头声称"技能调用未找到相关信息"而实际本次**没有发生工具调用**——轻微幻景，结论无害。

## 结论

- **两档模型都能胜任这套 RAG 流程**，14 题均无硬性编造数值/周期的失败。
- **30b-a3b 综合最优**：速度快一倍（MoE 只激活 3B）、答案组织更好；唯一失败是"偶发性跳过检索"，属于所有 LLM 的共性风险。
- **8b 是合格的轻量备选**：纪律执行意外地稳（14/14 有引用、3/3 拒答），速度也可接受；代价是答案更简略、偶发"幻景式工具声明"。
- MiniCPM5/qwen3:1.7b 这类 1~2B 模型连工具调用都不稳定，不适合本场景（详见下节实测澄清）。

*测试脚本：会话内生成（登录 → 逐题 POST /api/chat → SSE 解析 → 自动评分），原始数据 `/tmp/rag_report.json`。*

## 附：MiniCPM5 function-calling 实测澄清（2026-09-05）

网上流传"MiniCPM5 输出自研 XML 格式、Ollama 缺解析器、需换 SGLang"的说法，在本机（ollama 0.33.3 + openbmb/minicpm5）实测**不成立**：

| 测试 | 结果 |
|---|---|
| 简单匹配场景（get_weather + 天气问题） | ✅ 标准 OpenAI JSON `tool_calls`，无 XML，无需额外解析器/后端 |
| 工具与问题语义不匹配（skill_run"查手册" + 安装指导问题） | ❌ 模型自行判断"这不是知识库查询"后拒绝调用 |
| 带 300 token 上限的调用 | ❌ 假故障：思考块吃掉预算，看起来"content 空、没调工具" |
| liteclaw 全链路（车辆问答必须调 manual-rag） | ❌ 不稳定：1B 模型不服从"必须先调工具"的强规则，按自己的判断拒绝 |

结论：它的 function-calling **管道完好**（另一台 ollama 0.32.14 机器同样验证通过，两台环境无差异），短板在**规则纪律**——工具描述与用户问题存在语义距离时，大模型（30b/8b）靠服从系统提示硬调，1B 靠自己的判断经常拒绝。这是参数量决定的能力，换推理后端解决不了。适用定位：单一明确工具的轻量 Agent（天气/快递类查询）、无工具闲聊；不适合车书助手这类强制检索流程。给它的工具调用请放宽 token 预算（思考块 500~2500 字符起步）。
